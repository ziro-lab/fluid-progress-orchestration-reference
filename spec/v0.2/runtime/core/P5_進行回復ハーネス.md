# P5_進行回復ハーネス
## FPO v0.2 / module v0.8

### 役割

Active Blocker Setを所有し、原因区別・回復材料の統合・rollback採用を行い、通常Authorityへ安全に戻せる状態を作るRecovery Hub。

### Authority boundary

P5が所有するもの:

- Blocker case / set lifecycle
- observation / research / diagnostic resultの採否
- realized Progress claim
- recovery routeの採用
- diagnostic recoveryにおけるcheckpoint維持または後退
- suspend / terminal proposalの根拠

P5が所有しないもの:

- Source / Definition変更（P1）
- Design / Validation Method変更（P2）
- Target / Artifact修正（P3）
- criteria verdict / Acceptance（P4）
- successful closure（P6）

### Process

1. Blocker Setの全open item、scope、dependency、origin、symptom、attemptを確認する。
2. J3で必要なM・Capability classを選ぶ。
3. M07で継続・切替・待機・Human・terminal proposalのPolicyを決める。
4. diagnostic observation / research / safe probeを取得し、root-cause lifecycleを更新する。
5. expected deltaとrealized net deltaを比較し、material Progressだけをadoptする。
6. recovery actionを本来のowner stageへ返し、currentな最後の成立地点を決める。
7. 各Blockerをresolution evidence付きで個別にcloseする。
8. open Blockerが0件になった場合だけBlocker Setをresolveし、`interrupt_ref = null` とする。

### Rollback rules

- Source / Definition validityが失われた → `none`
- Design / Validation Method変更が必要 → `defined`
- Target / Artifact変更またはExecution再採用が必要 → `designed`
- Target、Execution、Design、Validation Methodが不変でEvidence取得だけ再試行可能 → `executed`を維持可能

P5自身がTargetを変更した状態で`executed`を維持してはならない。
P5はcheckpointを前進させない。

### Budget / terminal

Hard budget、Safety、Capability absence、unsatisfiable conditionにより自律経路が尽きた場合、M07のPolicyに従い、pause/approval待ち、分割、terminal dispositionをWork Controlへ提案する。

### Diagnostic effects

安全な診断probeもEffect Contractに従う。
通常成果物への修正はP3へ返す。

### 制約

一件解消で残存Blockerをclearしない。
Strategy変更やCapability利用だけをProgressとしない。

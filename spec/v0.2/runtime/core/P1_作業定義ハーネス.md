# P1_作業定義ハーネス
## FPO v0.2 / module v0.7

### 役割

immutableなSource RequestとAmendmentから、何を成立させるか、何を後続裁量へ委ねるか、どの優先規則で判断するかを確定する。

`WORK_DEFINITION_CONTRACT.md` をDefinition Recordの正本契約として使用する。

### Work Admissibility

通常Lifecycleへ進める前に、次を確認する。

- finiteである
- MUST Acceptance Criteriaを列挙できる
- 外部Effectをboundedに識別できる
- Acceptanceを十分に観測できる
- 一つのglobal checkpointが有意味である
- 必要Contextを参照から再取得できる
- 必要Capabilityが存在するか、取得可能性を評価できる
- Risk Tierが`T0`〜`T2`で、v0.2のDomain境界内である

不適合なら内容を一workへ押し込まず、分割案、必要外部Runtime、unsupported理由をBlockerとして返す。

### Definition outputs

- immutable source request refs / amendment refs
- purpose and scope
- Acceptance Criteria（stable ID、MUST / SHOULD、適用条件）
- requirement coverage map
- assumptions（根拠、影響、可逆性、再確認条件）
- design discretion
- rejected / deferred interpretations and reasons
- decision policy
  - priority order
  - quality floor
  - risk posture
  - prefer reversible
  - hard resource limits
  - trade-off rules

### Intent Fidelity

各Source clauseを、Acceptance、Design discretion、deferred、rejectedのいずれかへ追跡する。
追跡不能な要求を黙って落とさない。

高曖昧・高影響・T2・source item多数など `WORK_DEFINITION_CONTRACT.md` の条件に該当する場合、独立CapabilityによるSource→Definition coverage reviewを要求する。
Reviewerの結果は提案であり、採否はP1が所有する。

### Uncertainty

次はHumanへ返さず処理してよい。

- trusted inputsから一意に導ける
- Acceptance意味を変えないDesign discretion
- 可逆・低影響でDecision Policyにより決定可能なdefault
- Research / observation / domain capabilityで解消可能

次は推測せずActive Blocker化する。

- Acceptance、scope、不可逆性を変える複数解釈
- Authority / Approval不足
- 本人固有Preferenceで代替不能
- 必須Evidenceが人間・物理環境からしか得られない
- Work Admissibility不成立

### checkpoint

Definition record、coverage、Decision Policy、根拠をvalid commitへ保存した後だけ `defined` とする。

### 制約

Design、操作、Capability binding、Verification methodを決めない。
Source Requestを上書きしない。Amendmentはappend-onlyで扱う。

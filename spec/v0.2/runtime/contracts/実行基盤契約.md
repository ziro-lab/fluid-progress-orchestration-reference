# 実行基盤契約
## FPO v0.2 / contract 0.2

### 役割

FPO Policy Kernelと外部Operational Planeを、安全・durable・再開可能に接続する最低限の意味を定める。

具体的なDB、lock、queue、Agent API、OS process方式は指定しない。

### Runtime preflight

workをdispatchする前に次を確認する。

1. Bundle identityと `RUNTIME_MANIFEST.md` のhash整合
2. runtime規範外文書をControl Contextへロードしていない
3. latest committed state chainが一意・schema-valid
4. current projectionとcommit chainが一致
5. Work Control lifecycleが`active`
6. Bundle / policy / state revisionにstale writerがない
7. AuthorityとApprovalが有効

不一致を推測修復せずfail closedする。

### Common record semantics

immutable domain Record、projection snapshot、Commit、Dispatch Packet、Capability Return messageは `../schemas/fpo_records.schema.json` に従う。
work instance側の安定alias（例：WORK_STATE.md、WORK_CONTROL.md、WORK_INDEX.md）はlatest committed snapshotを指す再構築可能なcacheであり、それ自体を正本にしない。

immutable FPO Recordは最低限次を持つ。

- record type / schema version
- immutable record ID / logical ID / record revision
- work ID（global recordを除く）
- base state revision / sequence
- actor identity / role / Authority
- created_at
- bundle / policy revision
- sensitivity / retention class

recordはimmutableとし、変更は新record revisionで表す。
Machine-authoritative dataはMarkdown front matterに置き、bodyはTask / Evidence narrativeとして扱う。

### Machine record map

- Achievement: `work_state`
- Work boundary / intent: `source_request`、`work_admission`、`work_definition`
- Design / execution: `validation_method`、`execution_plan`、`plan_unit_state`、`artifact_manifest`
- Recovery: `blocker_set`、`blocker`、`progress_claim`
- Delegation / Effect: `delegated_operation`、`effect`
- Validation: `evidence`、`criteria_verdict`
- Control: `work_control`、`control_event`、`approval`、`resource_budget`、`terminal_settlement`
- Trust / durability: `capability_entry`、`ledger_event`、`current_projection`、`commit`
- Trusted outbound task message: `dispatch_packet`
- Untrusted provider input: `capability_return` message

Record typeを追加する場合は、Authority、lifecycle、projection/replay、retention、fixture、fault testを同時に定義する。単なるログ種別をCore stateへ昇格させない。

### Commit unit

意味上のsource of truthはappend-only commit chainである。Current projectionは再構築可能なcache / indexとする。

1. Candidate recordをimmutableにpersistしschema検証する。
2. 各recordのSHA-256を計算する。
3. parent_commit_id、expected_state_revision、新revision、record digest、Authority decisionを持つcommit recordを作る。
4. expected revisionのCASまたは同等の排他でcommit recordを一意にpublishする。
5. current projection / pointerを更新する。

commit record publish前にcrashしたCandidateはorphanであり採用しない。
commit publish後にprojection更新前でcrashした場合、commit chainからprojectionを再構築する。

### Replay / projection

`CURRENT_PROJECTION` は少なくとも次を参照する。

- current WORK_STATE / WORK_CONTROL
- adopted definition / design / Execution Plan
- current `plan_unit_state` refsと再構築可能なPlan Unit cache
- active Blocker Set
- open Operation / unresolved Effect
- current Evidence index / open criteria
- current approvals / latest `resource_budget` refとBudget cache
- open obligations
- recent event window / archive refs

Runtimeは通常再開時にcurrent projectionと必要なstage packetだけを読み、全履歴を毎回LLMへ投入しない。
Compactionはsource refsとcoverage checkを持ち、原記録を根拠なく削除しない。

### State update / stale writer

各updateはbase_state_revisionとAuthorityを持ち、current revisionと一致する場合だけcommitする。
遅延Return、古いP段階、古いApproval、旧bundleからのupdateを拒否またはsupersede候補として隔離する。

### Operation / Effect orchestration

- Operation lifecycle、cancel、reconcileは `DELEGATED_OPERATION_CONTRACT.md`
- Effect lifecycle、compensationは `EFFECT_RECOVERY_CONTRACT.md`
- duplicate / out-of-order updateをidempotently処理
- unknown outcomeを自動成功・自動retryしない
- cancel時は新規Effectを止め、Operation cancelとEffect reconcileを行う

### Work Control

suspended / canceling / terminated workをJ1へdispatchしない。
Budget、deadline、Approval expiry、user eventを監視し、`WORK_CONTROL_CONTRACT.md` に従う。

### Trust enforcement

Control / Task / Evidence / Untrusted Inbox / Secret Storeを論理・可能なら物理分離する。
Schema validation、least privilege、sandbox、egress/path scope、output sanitizationを実行する。

### Retention / redaction / archive

recordごとにsensitivity、retention class、expiry、legal holdを適用する。
Redactionは監査chainを壊す上書きではなく、`ledger_event.event_type = redaction | tombstone`とdigest provenanceで表す。専用Record typeを暗黙に増やさない。
closed / terminated後はcurrent projectionを固定し、archive / GC対象を区別する。

### Runtime boundary

大量並列、multi-work scheduling、continuous monitoring、特定providerのdurability実装はv0.2の範囲外。
ただし本契約のcommit、cancel、reconcile、Authority、Trust、Evidence不変条件を満たさないRuntimeをFPO適合と呼ばない。
